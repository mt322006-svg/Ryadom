# Product Principles

## Main rule

Build the core first.

Everything in the first version should support speed, clarity, and reliability — and make **kindness practical**: easy to offer, easy to accept, safe enough to repeat.

## Keep

- fast request creation
- approximate location instead of exact exposure
- one clear action per step
- simple language
- calm visual hierarchy
- lightweight trust signals
- early safety guardrails

## Avoid

- feature sprawl
- heavy forms
- chat before a match is made
- marketplace thinking
- monetization that changes helper behavior (commissions, paid boosts, helper rankings for sale)
- in-app payment rails before the core loop is proven on real devices
- social noise that distracts from help
- premature optimization
- blind trust without boundaries

## Money and compensation

- **Free help** is the default mental model.
- **Paid** between people may exist as a label on a request («договорились сами»), but the app does not take a cut and does not push paid over free.
- The product must not optimize for revenue per request. It optimizes for **time-to-help** and **trust**.

## Interaction principles

- a request should feel like a situation, not a listing
- nearby context should feel alive, not cluttered
- helpers should be discoverable quickly
- the user should understand the next action immediately

## Decision filter

When a feature idea appears, ask:

1. Does this make help faster?
2. Does this make the flow clearer?
3. Does this increase trust without adding friction?
4. Does this stay honest if the repo is public and the app is free?

If the answer is mostly no, the feature likely belongs later.
